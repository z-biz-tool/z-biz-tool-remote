## 1. 用户旅程全景与断点定位

`登录/注册 → 发现设备 → 配对/授权 → 建立会话 → 观看屏幕 → 注入输入 → 切换多屏 → 文件传输 → 聊天协作`，旁路：`断线重连`、`结束/审计`。

| 环节 | 状态 | 断点根因 |
| --- | --- | --- |
| 登录/注册 | ✅ 可用 | —（已有 refresh 轮换、预刷新、401 重放） |
| 发现设备 | ⚠️ 部分 | 「我的设备」有租户过滤；「在线设备」越权全量（S-03） |
| 配对/授权 | ⚠️ 部分 | Token 明文长显（C-22）、无 SAS 核对、信任列表可篡改（C-17）、`sameUser` 死代码（S-16） |
| 建立会话 | ❌ **断** | `JOIN_SUCCESS` 后**不切视图**（G2-1）；`CONTROL_ACCEPT` 不建会话（S-17） |
| 观看屏幕 | ⚠️ 部分 | 能出画面，但每帧全量 JPEG+base64（C-25/C-28），无自适应（C-29） |
| 注入输入 | ❌ **断** | 鼠标可用；**键盘完全无监听**（C-01）→ 远程打字不存在 |
| 切换多屏 | ❌ **断** | Rust 底座已具备，控制端无切屏 UI（C-09） |
| 文件传输 | ❌ **断** | 三处都断：server 无路由（S-15）、发送格式错（C-04）、接收无落盘（C-03） |
| 聊天协作 | ❌ **断** | 组件完整但未挂载（C-06）+ server 无 case（S-15） |
| 断线重连 | ❌ **断** | 断连即删会话（S-19）、重连不恢复（C-38）、固定间隔惊群（C-37） |
| 结束/审计 | ⚠️ 部分 | `onStop` 只清本地不通知服务端（C-23）；无 `LEAVE_SESSION`（S-18）；无审计日志 |

**结论：11 个环节中 5 个完全断、4 个部分可用、2 个可用。** 「看起来能用、实际不能用」是当前最大的产品风险。

## 9. 文件传输（G8）——协议需重设计

当前三处都断（S-15/C-03/C-04），且现有 base64 字符串分块方案**格式本身错误**，不能靠补服务端路由修好。建议三步重设计：

1. **控制面（JSON over WS，复用信令连接）**：`FILE_OFFER{transferId,name,size,sha256,direction}` → 被控端弹确认 → `FILE_ACCEPT`/`FILE_REJECT{reason}`；传输中 `FILE_PROGRESS{sent,total}`；结束 `FILE_DONE{sha256}`/`FILE_FAIL{code}`。
2. **数据面（二进制帧，走媒体通道）**：`channel=0x02`，负载为**原始字节分块**（默认 64KB/块），块头带 `transferId`+`chunkIndex`；**不做 base64**（省 33% 体积与 CPU）；接收端按 `chunkIndex` 拼装并边收边算 sha256。
3. **落盘与边界**：接收端必须弹 Tauri `dialog` 让用户选保存目录（禁止写死路径、禁止自动落盘）；单文件默认上限 2GB 可配；可执行扩展名黑名单默认拦截并需 L2 强确认（见 [04](./04_数据安全与可靠性.md) §6/§7）；受 `allowFileTransfer` 真实开关约束（修 C-07）。

| # | 缺口 | 优先级 |
| --- | --- | --- |
| G8-1/G8-2/G8-3 | server 无任何 `FILE_*` case；发送端 data URL + 字符切分格式错误；接收端无拼装/落盘/路径选择 | **P0**（三者共同构成能力前提） |
| G8-7 | 无危险扩展名拦截 | **P0**（安全红线） |

## 11. Agent 辅助（G10）——定位与红线

**判断：仓库根的 `src/agent/` 是 SQL Agent 模板残留，与远程控制无关，不应接入。** 远程控制场景下 Agent 的能力上限必须低于 SQL 场景，理由是**结构性**的：SQL 语句在执行前**可被人读懂并审查**，所以「人确认」是有效安全阀；而远程输入事件序列（数百个坐标 + 按键码）**人类无法阅读**，「确认」退化为无意义的点按钮。一旦允许 Agent 自主发起 `simulate_input`，等价于把一台机器的完全控制权交给不可审查的自动流程。故产品定位收敛为**「只读 + 建议」**：

| 允许 | 禁止（永久） |
| --- | --- |
| 读连接质量并给出降画质建议；汇总当前会话审计事件；生成「操作步骤说明」供人阅读；提示异常（如被控端长时间无帧） | 自主调用 `simulate_input`；自主发起文件写入/传输；自主调用 `shell`/`fs` 插件；自主修改授权、信任列表、权限档位 |

落地：Rust 侧 `simulate_input(event, origin)`，`origin.source == "automation"` 时**无条件拒绝**（不可被 JS 绕过）；所有 Agent 建议必须由真人点击后才产生副作用。完整论证与红线见 [04](./04_数据安全与可靠性.md) §8。
缺口：**G10-1** 无 `origin` 参数，任何 JS 都能触发注入（**P0**）｜**G10-2** 孤儿 `src/agent/` 可能被误接入（P2，删除或明确隔离）｜**G10-3** 无「连接质量建议」类只读助手（P2）。

## 14. 明确**不引入**的能力（避免范围蔓延）

1. **WebRTC / P2P 打洞**：全中继架构契合「自托管单文件中继」定位且可审计；折中方案是可选的局域网直连（见 [03](./03_技术架构与性能优化.md) §8）。
2. **音视频通话与语音对讲**：与远程控制主流程无关，且显著放大隐私风险。
3. **无人值守远程开机（WoL）/ BIOS 级控制**：需额外硬件与驱动，超出本项目边界。
4. **移动端被控（Android/iOS）**：权限模型完全不同，会拖累桌面侧收敛。
5. **多租户组织 / RBAC / SSO**：当前是个人与小团队自托管工具，账号维度已足够；企业目录集成属另一产品。
6. **录制回放 / 会话录像云存储**：留存屏幕录像的隐私与合规成本远高于收益；仅允许控制端本地手动截单帧（G3-9）。
7. **Agent 自主操作**：见 §11 的结构性论证，这是**永久红线**而非阶段性取舍。
