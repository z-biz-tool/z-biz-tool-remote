## 1. 优先级定义与角色

**P0** = 安全红线或阻塞构建，未完成不得对外发布 ｜ **P1** = 已声明但不可用的能力，或显著性能/可靠性缺陷 ｜ **P2** = 体验与运维增强。
角色：**FE** 前端 React/TS ｜ **RS** 客户端 Rust/Tauri ｜ **BE** 服务端 Node ｜ **DEVOPS** CI/Docker/发布 ｜ **QA** 测试 ｜ **SEC** 安全评审。工期单位 **pd**（人日），假设单人全职、含自测、不含评审等待。

## 8. 依赖关系与关键路径

四条可并行的关键链：`A07(Win编译) → A05/A08(CI bundles) → A03(CI 修路径)` ‖ `B01(成员表) → B02/B03/B04/B16 → S2-04 → S2-05` ‖ `B07(token 移出 URL) → B12(客户端 HELLO) → S2-09(配对码) → S2-10(授权弹窗) → S5-02(pinning)` ‖ `S3-01(双通道) → S3-02(帧头) → S3-03(Rust 推流) → S3-04(脏区) → S3-09/S3-10 → S5-01(E2EE)`。

强约束：**A07 必须最先做**（否则 Windows CI job 持续失败，跨平台改造无法验证）｜**B01（成员表）是 8 个后续任务的共同前置**，必须一次做对（含 `role`/`state`/`permission` 三字段）｜**S3-03（Rust 推流）是 S3-04/S3-09/S4-10/S5-01 的前置**，也是 S3 最大风险点｜**S5-01（E2EE）依赖 S3-02 的帧格式**不能提前，但 B09/B10（删除假 `encryptionKey`）必须**先于** S5-01，避免两套加密语义并存｜S2 与 S3 **可部分并行**（S2 主要是 JS/协议路由，S3 主要是 Rust），但需 BE 协调 `server.js` 的冲突改动。

## 9. 兼容性、迁移与回滚

**协议兼容**：`HELLO` 版本协商是所有改造的兼容基础。S1 起服务端记录 `protoVersion` 并保留 **N-1 版本兼容分支**（一个发布周期）。破坏性变更（删 `encryptionKey`、token 移出 URL、`INPUT_EVENT` 加鉴权）**不做兼容**——它们修的是安全缺陷，旧行为必须立即失效；代价是 **client 与 server 必须同版本发布**，需在 README 与发布说明中明示。

**数据迁移**：① 客户端 token `localStorage`/`state.json` → OS 密钥库，迁移后立即从原位置删除并覆盖写盘（C04）｜② 历史记录剥离 `sessionToken` 字段（C03）｜③ 服务端 `data.json` → SQLite，提供 `migrate.js` 一次性脚本 + 迁移前自动备份 + 迁移后校验计数（S4-08）｜④ refresh token 改存散列无法逆向，切换时**强制所有用户重新登录**（提前公告）。

**回滚与灰度**：每阶段独立可回滚——S1-A revert workflow/Dockerfile 提交即可；S1-B/C/D 属安全修复，**不建议回滚**，若必须则走特性开关（`ALLOW_INSECURE_LEGACY=true`，默认 false，仅内网测试用）；S3 客户端保留 E0 旧采集路径由设置项切换（一个发布周期后删除）；S4-08 保留 `data.json` 导出能力；S5-01 用帧头 `flags.bit2` 标识是否加密，服务端两种都转发，客户端可降级（UI 显示警示色）。灰度：S3/S4/S5 按「内部设备 → 自愿测试用户 → 全量」三档；**S1 安全改造不灰度、直接全量**（灰度意味着部分用户仍暴露在越权链下）。

## 10. 资源假设与路线风险

资源假设：1 BE + 1 RS + 1 FE + 0.5 DEVOPS + 0.5 QA + 0.2 SEC，S1–S5 总工期约 **180 pd**（约 4.5 人月，按上述配置并行后**日历时间约 8–10 周**）。工期为估算，不含需求评审、设计走查、发布等待与线上问题回插。

RK-01 S3-03 Rust 推流是新技术栈（tokio + tungstenite），团队经验不足 → 先做 1 pd spike 验证；失败则退化为「JS 层收 `ArrayBuffer` 但帧仍由 Rust 编码」的中间方案｜RK-02 E2EE 与「服务端可审计」张力 → 帧头保持明文供路由统计，审计只记元数据不记内容｜RK-03 SQLite 引入原生依赖使 Docker 构建复杂化 → 用 `better-sqlite3` 预编译二进制，或推迟到 S4 之后（C05 已覆盖最紧急的权限与散列修复）｜RK-04 client/server 必须同版本发布 → `HELLO` 协商 + 明确升级提示 + `release.sh --both` 修好后一键双发（A06）｜RK-05 强制 TLS 抬高自托管门槛 → 提供内置 Caddy/Traefik 自动签发 Let's Encrypt 的 compose 示例，本地开发豁免 `localhost`｜RK-06 删除 `encryptionKey`/`fs:default`/`shell:default` 可能影响隐式依赖 → 已 grep 确认全仓无调用，仍在 G-S1 跑全量 E2E｜RK-07 现有 2 个 E2E 在 S1 后会失败（鉴权变严）→ **禁止删除断言**，只允许更新断言以匹配新的正确行为（[06](./06_测试验收与风险清单.md) CT-12）｜RK-08 键盘输入跨平台/输入法差异大 → 用 `e.code` 而非 `e.key` + 平台按键映射表 + QA 覆盖三平台 × 中英输入法｜RK-09 速率限制误伤 NAT 后多用户 → 按「IP + 账号」双维度并提供白名单配置｜RK-10 审计日志增长 → 被控端环形缓冲、服务端保留期可配 + 轮转｜RK-11 工期偏乐观（未含跨平台实机调试）→ S4 预留 20% buffer，Windows/Linux 实机测试列为独立任务｜RK-12 `_shared/` 孤儿组件可能与 antd 6 / React 19 不兼容 → 挂载前先跑编译验证，不兼容则重写而非硬接｜RK-13 旧实例升级后 refresh token 失效需重登 → 提前公告 + 低峰窗口 + 批量重登指引。

## 11. 交付物与明确不在路线内

**每阶段交付物**：代码改动 + 对应测试（[06](./06_测试验收与风险清单.md) 矩阵中标注了阶段归属）+ 出口门禁通过记录 + 协议变更说明（若有）+ 回滚预案；S1 额外交付**安全修复说明**（列出已堵的攻击链，供 SEC 评审）。
