## 1. 当前传输链路的逐跳成本

`xcap截屏BGRA → image缩放(Triangle/纯CPU) → JPEG全帧编码 → base64(+33%) → IPC Rust→JS → JSON.stringify转义再膨胀 → WS文本帧 → 服务端parse+重新stringify → WS文本帧→控制端 → img src=data:URL每帧完整解码`

主要浪费：每帧 `Monitor::all()` 重枚举（C-26，15fps = 每秒 15 次系统调用）；全帧 JPEG 无差分（C-28，桌面 >80% 时间基本静止）；base64 使体积 +33% 并多两次编解码（C-25）；JSON 文本帧导致转义膨胀与服务端 `parse`→`stringify` 双次序列化（C-25/S-21）；每帧 2 次 IPC（C-25）；同步 command 阻塞命令线程且无 tokio（C-27）；`<img src=data:…>` 每帧重建 DOM 属性无 canvas 复用（C-32）；`mousemove` 逐事件发送（C-30）；无 `maxPayload` 与背压（S-22/S-23）。

## 2. 通信协议推荐契约

### 2.1 双通道分离

| 通道 | 内容 | 编码 | maxPayload |
| --- | --- | --- | --- |
| **信令通道** | 注册、设备列表、会话建立、授权、文件控制面、聊天、心跳 | JSON 文本帧 | 64KB |
| **媒体通道** | 屏幕帧、输入事件、文件数据面 | **二进制帧** | 8MB |

分离理由：信令要求可靠可读、低频小包；媒体要求低开销高吞吐。混在一条连接上会让背压策略互相干扰（一个大帧就能阻塞授权消息）。

### 2.2 二进制帧头（小端，固定 24B + 可选 4B 扩展）

`magic(1)=0x5A` `version(1)=1` `channel(1)` `flags(1)` `codec(2)` `sessionId(4)` `seq(4)` `captureTsMs(4)` `displayId(2)` `width(2)` `height(2)` `payloadLen(2)`；当 `flags.bit3=1` 时追加 `extPayloadLen(4)` 以支持 >64KB 负载。

- `channel`：`0x01`=screen，`0x02`=file，`0x03`=input，`0x0F`=control
- `flags`：bit0=keyframe，bit1=dirtyTiles，bit2=encrypted，bit3=hasExt
- `codec`：`0`=JPEG，`1`=PNG，`2`=H.264，`3`=VP9（预留）
- 脏区块表（`flags.bit1=1` 时置于负载前）：`tileCount(2)` + 每项 `tileX(2) tileY(2) offset(4) len(4)`，tile 固定 64×64

**关键设计**：帧头**不加密**（服务端需 `sessionId`/`channel` 做路由），仅负载加密。中继无需解密即可转发，同时保证内容机密性（详见 [04](./04_数据安全与可靠性.md) §3）。

### 2.3 输入事件二进制化（`channel=0x03`，固定 16B）

`eventType(1)` `buttons(1)` `x(4 float32 归一化0..1)` `y(4 float32)` `keycode(2)` `modifiers(2)` `seq(2)`。
`eventType`：1=move 2=down 3=up 4=wheel 5=keyDown 6=keyUp 7=keyType(变长) 8=hotkey。
坐标用**归一化浮点**而非绝对像素，天然解决多屏分辨率差异导致的错位（修 G5-4）。

### 2.4 信令消息新增/修正契约

| 消息 | 方向 | 关键字段 | 修正点 |
| --- | --- | --- | --- |
| `HELLO` / `HELLO_ACK` | C↔S | `protoVersion`, `clientVersion`, `platform`, `caps[]` / `negotiatedVersion` | **新增**版本协商；不兼容回 `ERROR{code:VERSION_MISMATCH}` |
| `REGISTER` / `REGISTER_SUCCESS` | C↔S | `deviceId`, `deviceName`, `token` / `userId`, `serverPubKey` | 服务端**必须校验 deviceId 归属**（S-04/S-05）；token 改走首条消息而非 URL query（S-11）；**删除 `encryptionKey`**（S-06/C-05），改下发服务端长期公钥供 pinning |
| `GET_ONLINE_DEVICES` | C→S | `scope` | 默认 `scope:"mine"`；**移除全量枚举能力**（S-03） |
| `CONTROL_REQUEST` | C→S→H | `targetId`, `sessionId?`, `requestedPermission`, `sasHash` | 转发必须带 `requestedPermission` 与 `sasHash`（修 S-16 丢字段） |
| `CONTROL_ACCEPT` / `CONTROL_ACCEPTED` | H→S→C | `sessionId`, `grantPermission` / `sessionToken`, `role` | 服务端据此**真正创建会话 + 生成 token**（修 S-17） |
| `SCREEN_FRAME` | H→S→C | 二进制帧 | 走媒体通道；服务端**必须校验发送者是 host**（S-02），并透传 `seq`/`captureTsMs`（S-21） |
| `INPUT_EVENT` | C→S→H | 二进制帧 | 服务端**必须校验 sender ∈ sess.clients 且 role=client**（S-01） |
| `SELECT_DISPLAY` / `DISPLAYS_CHANGED` | C→S→H / H→S→C | `displayId` / `displays[]` | **新增**，替代塞进 `INPUT_EVENT` 的 `screen-select`（C-08/C-09） |
| `LEAVE_SESSION` / `KICK_CLIENT` | C→S / H→S | `sessionId`, `reason` / `targetId` | **新增**，替代 `closeSession()` 发 `PONG` 的假实现（S-18）；被控端主权 |
| `SESSION_MEMBERS` | S→C | `members[{id,role,joinedAt,state}]` | **新增**，成员可见性 |
| `CLIENT_STALE` / `RESUME_SESSION` | S→C / C→S | `graceUntil` / `resumeToken` | **新增**，断线宽限与恢复（S-19/C-38） |
| `REQUEST_KEYFRAME` | C→S→H | `sessionId`, `reason` | **新增**，加入/重连/丢帧后立即要全帧 |
| `PAUSE_STREAM` / `RESUME_STREAM` | C→S→H | `sessionId` | **新增**，多标签页单路活跃推流（T-25） |
| `PING` / `PONG` | 双向 | `ts` | **统一为唯一应用层心跳**，供 RTT 统计；协议层 ping 仅回收僵尸连接（S-20） |
| `FILE_OFFER/ACCEPT/REJECT/PROGRESS/DONE/FAIL` | C↔S↔H | `transferId`, `name`, `size`, `sha256` | **新增**控制面（见 [02](./02_产品能力与交互优化.md) §9）；数据面走 `channel=0x02` |
| `CHAT_MESSAGE` | C↔S↔C | `sessionId`, `text`, `ts` | **新增**，限长 4KB、限速 5/s、**校验成员** |
| `ERROR` | S→C | `code`, `message`, `retryable` | 建立错误码表；`UNKNOWN_TYPE` 保留用于协议违规检测 |

### 2.5 服务端处理硬性要求

`maxPayload` 按通道分设（修 S-22）；**背压**：`send()` 前检查 `ws.bufferedAmount > 8MB` 则丢帧（屏幕帧可丢，输入与信令不可丢）并计数上报（修 S-23）；**鉴权前置**：所有 `case` 进入前先过 `assertSessionMember(sessionId, deviceId, requiredRole)`，未通过直接 `ERROR{code:FORBIDDEN}` 并写审计；会话成员表 `sess.clients: Map<deviceId,{role,joinedAt,state,ws}>` 是 S-01/S-02/S-03 的统一修复基础。

## 3. 屏幕采集与编码

### 3.1 分阶段演进（不要求一步到位）

| 阶段 | 方案 | 依赖 | 预期收益（**假设**） |
| --- | --- | --- | --- |
| E0 | 现状：JS `setInterval` + 全帧 JPEG + base64 + JSON | — | 基线 |
| **E1** | **Rust 侧自主推流**：`start_capture(streamId, params)` 启后台任务，帧经 Rust WS 客户端直发，**不再回 JS** | 新增 `tokio` + `tokio-tungstenite` | 消除每帧 2 次 IPC 与 base64（体积 −33%） |
| **E2** | 脏区（tile）增量编码 | E1 | 静态画面码率 −70%~−90% |
| E3 | 硬件加速编码（VideoToolbox / Media Foundation / VAAPI）+ H.264 | E1，每平台一套 | 1080p@30fps 可达，CPU 大幅下降 |
| E4 | WebCodecs 解码侧加速 | E3 | 控制端解码开销下降 |

**建议 S3 阶段只做 E1+E2**；E3/E4 列为后续独立评估项——硬件编码器跨平台成本高，且会破坏「单文件中继不解析内容」的简洁性与可审计性。

### 3.2 Rust 侧立即优化（不改架构即可做）

A-1 缓存 `Monitor` 句柄，仅在 `DISPLAYS_CHANGED` 或采集报错时重枚举（`capture.rs`，修 C-26）｜A-2 `capture_screen`/`capture_monitor` 改 `async` + `spawn_blocking`（`commands.rs`，修 C-27）｜A-3 缩放算法可配，默认 `Triangle`、低配机降 `Nearest`，4K 源先降采样到 2× 目标再精缩（`capture.rs` L61，修 C-34）｜A-4 `Enigo` 用 `thread_local!` 复用，避免每事件重建（`input.rs` L76，修 C-33）｜A-5 release profile 分包：`[profile.release.package.image] opt-level=3`，其余保持 `"s"`（`Cargo.toml`，修 C-35）｜A-6 JPEG 用 `JpegEncoder` 直写 `Vec<u8>`，避免中间 `DynamicImage` 拷贝（`capture.rs` L67–L83）｜A-7 **规划新增** `src-tauri/src/capture_diff.rs`，提供 `capture_diff` 命令返回脏区列表 + 分块 JPEG，供 E2 使用。

### 3.3 脏区（tile）算法

```
GRID = 64x64 px, THRESH = 12, KEYFRAME_INTERVAL = 30
每帧:
  1. 当前帧与上一帧逐 tile 取 8 个采样点(4角+4边中点)比较 RGB
  2. 任一采样差异 > THRESH → 该 tile 标记 dirty
  3. dirtyRatio = dirtyTiles / totalTiles
       == 0     → 跳过本帧不发；仅在 KEYFRAME_INTERVAL 边界发全帧
       > 0.40   → 退回全帧编码(分块头开销已超过收益)
       其余     → 只编码 dirty tiles，帧头置 flags.bit1
  4. 每 KEYFRAME_INTERVAL 帧无条件发 keyframe，防累积漂移
  5. 收到 REQUEST_KEYFRAME → 立即发 keyframe 并重置 prev 缓存
```

控制端维护 `tileCanvas`，按 `tileX/tileY` 贴回；收到 keyframe 时整幅重建。

### 3.4 带宽自适应

评估周期 2s，输入 = 平滑 RTT + 丢帧率 + `bufferedAmount`；**带滞回**（升档需连续 2 周期满足，降档立即执行）。降级顺序：**先降 fps → 再降质量 → 最后降分辨率**（分辨率突变感知最差）。

| 档位 | 最大帧宽 | JPEG 质量 | fps | 目标码率（**假设**） | 触发 |
| --- | --- | --- | --- | --- | --- |
| L0 极省 | 640 | 50 | 8 | ≤0.8 Mbps | RTT>300ms 或丢帧>25% |
| L1 流畅 | 960 | 62 | 10 | ≤1.5 Mbps | RTT 150–300ms |
| L2 平衡（默认） | 1280 | 75 | 15 | ≤3 Mbps | RTT 60–150ms |
| L3 清晰 | 1600 | 82 | 20 | ≤6 Mbps | RTT<60ms |
| L4 原画 | 1920 | 88 | 24 | ≤12 Mbps | 局域网 / RTT<20ms |

用户选「自定义」时禁用自动升降档，但仍在 `bufferedAmount` 超限时强制丢帧保护。

## 4. 进程与连接模型

**客户端 Tauri**：`WebView(React UI) ⇄invoke/event⇄ Rust core`，Rust core 分出两条独立 WS：①**采集/编码任务(tokio)** → 媒体 WS 客户端（帧直发，不过 JS）；②信令 WS 客户端。**服务端 Node**：信令处理（鉴权/会话/成员表）↔ `SQLite(better-sqlite3)`；媒体中继（只路由不解码）。两条 WS 分别对接信令处理与媒体中继。

- **媒体帧不再经过 WebView**：Rust 采集→编码→直发媒体 WS；WebView 只收 `event` 通知统计值（fps/码率）。这一步同时消除 C-25 的 IPC 与 base64 开销。
- **控制端解码仍在 WebView**（渲染必须在 WebView），但接收走 Rust 转发 `ArrayBuffer`（Tauri 2 支持），不做 base64。
- **服务端存储换 SQLite**：`data.json` 全量重写（S-24）在设备数上升后是明显瓶颈；`better-sqlite3` 单文件、零运维、支持事务与索引，同时解决 S-24/S-25。**会引入原生依赖，需评估 Docker 构建体积**，故列为 S4 而非 S1。
- **水平扩展**：单进程内存态（S-26）多实例下失效。**建议先不引入 Redis**，而是让单实例支撑目标规模（§7），同时把 `clients`/`sessions` 抽象为 `Registry` 接口，未来可替换为 Redis 实现而不改业务代码。

## 5. 连接生命周期

### 5.1 客户端连接状态机（7 态）

主干：`Idle →(用户发起/自动重连) Connecting →(HELLO_ACK+REGISTER_SUCCESS) Online →(JOIN_SUCCESS/CONTROL_ACCEPTED) InSession →(WS断开) Stale →(RESUME_SESSION成功/30s宽限内) InSession`。

回落：`Connecting →(握手或鉴权失败) Failed →(退避重试≤10次) Connecting`，耗尽后 `Failed → Idle`（转手动重连）｜`Stale →(宽限超时收SESSION_CLOSED) Idle`｜`InSession →(LEAVE_SESSION) Online`｜`Online →(登出) Idle`。

### 5.2 重连退避（修 C-37）

`base=1s, factor=2, max=30s, jitter=±20%, maxAttempts=10`；`delay(n) = min(max, base*factor^n) * (1 + uniform(-0.2, 0.2))`；去抖动序列 `1,2,4,8,16,30,30,30,30,30`，总窗口约 3 分钟，耗尽后转「手动重连」。

### 5.3 服务端会话宽限（修 S-19）

```
on ws.close(deviceId):
  for sess in sessionsOf(deviceId):
    member.state="stale"; member.graceUntil=now+30_000
    broadcast(sess, CLIENT_STALE{deviceId, graceUntil})
  after 30s: if member.state=="stale" → 移除成员
             若缺席者是 host → 关闭会话并广播 SESSION_CLOSED
on RESUME_SESSION{sessionId, resumeToken}:
  校验 resumeToken 与该 deviceId 绑定 → member.state="active" → 回 SESSION_RESUMED
  控制端收到后立即 REQUEST_KEYFRAME
```

`resumeToken` 与 `sessionToken` **分离**：前者仅宽限期内有效且绑定 deviceId，避免长期凭证扩散。

### 5.4 心跳统一（修 S-20）

应用层 `PING{ts}`/`PONG{ts}` 间隔 15s、超时 2×间隔判失联，用于 RTT 统计与自适应输入；协议层 `ws.ping()` 间隔 30s 仅回收 TCP 半开连接（保留现有实现）；**禁止再用 `PONG` 承载「退出会话」语义**（现有 `closeSession()` 假实现必须删除）。

## 7. 并发多会话

**两步演进**：① **S4：多会话并存但单路推流**——UI 支持多标签页（复用孤儿 `_shared/AppShell.tsx`），同时只有一个活跃推流，切换标签时对后台会话发 `PAUSE_STREAM`/`RESUME_STREAM`；这解决 90% 真实需求且几乎不增加带宽。② **S5+：多路并发推流**——必须先落地 E1（Rust 侧推流），否则 JS 层多个 `setInterval` 会互相饿死。

**并发上限建议（假设值，需实测校准）**：被控端同时被控 **2** 路（每路 1080p@15fps 约 3Mbps 上行，家庭/办公上行常 ≤10Mbps）｜控制端 **1 活跃 + 3 暂停**（解码渲染开销集中在活跃路）｜单会话观看者 **3** 人（服务端 fan-out 带宽线性增长）｜服务端单实例在线连接 **2000**（Node 单进程 WS，无媒体解码开销）｜服务端单实例活跃会话 **200**（受 `SCREEN_FRAME` 转发 CPU 与出入带宽限制）。超限返回 `ERROR{code:CAPACITY_EXCEEDED, retryable:true}`，客户端明确提示而非静默失败。

## 8. 关于 WebRTC 的明确判断

`package.json` 的 `keywords` 含 `webrtc`，但**仓库内零 WebRTC 代码**（已 grep 确认）。

对比要点：全中继部署复杂度低（单 Node 进程 + `ws` 一个依赖）、NAT 穿透成功率 100%、**全部流量过自己服务器因而可审计可限权**、代价是服务器承担双倍出入带宽；WebRTC 需 STUN+TURN+ICE+SDP，对称 NAT 下仍需 TURN 兜底（等于回到中继），且 P2P 建立后**服务端失去可见性与管控点**。

**结论：不引入 WebRTC。** 全中继的可审计性是远程控制品类的安全资产，而本项目定位是自托管小规模场景，服务器带宽不是主要矛盾。
**折中方案（P2）**：可选**局域网直连**——双方经 `LAN_DISCOVER` 探测到同内网时，被控端起本地 WS 监听（**仅绑内网地址**），控制端直连，服务端保留授权记录。此路径**必须仍走 TLS、仍受被控端授权约束**（见 [04](./04_数据安全与可靠性.md) §3）。
