## 2. 调查记录

### 2.1 P0-1 的根因不是 `toWsUrl` 一行，是**整个仓库把「协议」当成了内部细节**

台账 C-14 只记了 `toWsUrl()` 恒定返回 `ws://`。查下来这是一串**同源**问题的最后一行：

| 位置 | 原行为 | 后果 |
|---|---|---|
| `storage.ts` `toWsUrl` | 先 `stripProtocol` 剥协议，再恒拼 `ws://` | 用户显式填 `wss://example.com` **实际连明文** |
| `storage.ts` `toWsUrl` 内的 `clean.startsWith("ws")` | **死代码**：`stripProtocol` 已剥掉前缀，`clean` 不可能以 "ws" 开头 —— 除非主机名自己以 ws 开头（`ws.example.com`），那时产出**没有协议的非法 URL** | 边界主机名直接坏掉 |
| `storage.ts` `DEFAULT_SETTINGS.serverUrl` | 写死公网 IP `101.37.80.51:8080` | 每个安装的二进制都默认连到某台机器 |
| `tauri.conf.json` `bundle.macOS.exceptionDomain` | 写死同一个公网 IP | 同上 |
| `storage.ts` `hydrateStorage` | `s.serverUrl = displayUrl(s.serverUrl)` —— **剥协议** | 重启后连本机地址时按缺省回落成明文 `ws://` |
| `storage.ts` `displayUrl` | 显示/存储都用它 → 协议无处安放 | **用户没有任何地方能表达「用 TLS」** |
| `api.ts` `serverUrlToHttpBase` | **是** TLS-aware 的（`wss:`→`https:`） | 证明别处都认 TLS，唯独连接层把方案扔了 ⇒ 断链点确实在连接层 |

⇒ 根因是**模型问题**：「协议」被当成不可见的东西，所以它既不能存、不能显、也不能被用户指定。
只改 `toWsUrl` 一行不够 —— 存储层还在剥它。

### 2.2 服务端**本来就支持 WSS**，断链只在客户端

- `z-biz-tool-remote-server/server.js:196-204`：`TLS_KEY_PATH && TLS_CERT_PATH` 时用
  `createHttpsServer`（原生 WSS），否则 `createHttpServer`。
- `server.js:39-40` 读 `TLS_KEY_PATH` / `TLS_CERT_PATH`；`server.js:668-672` 启动时按实际协议打日志。
- `.env.example` 里 TLS 两项已在。

⇒ 服务端能力齐备，**不需要新增任何依赖**就能走 TLS。缺口 100% 在客户端。

### 2.3 「带内加密」这条路本身是走不通的（P0-4 的定性）

- 帧与键鼠事件走 `ws.send(JSON.stringify(msg))` —— **明文 JSON**。
- 账号令牌在**同一条链路**的 URL 查询串里（`signaling.ts:538` `buildWsUrl` 拼 `?token=`）。
- ⇒ 没有 TLS 时，窃听者**连密钥一起**看到，带内再套一层加密是自欺欺人。

### 2.4 台账 05 已经写好了验收标准 —— 本轮按它做，不自创方案

`05_实施路线与任务拆解.md` S1-B11：
> `toWsUrl`（L310–L319）默认 `wss://`，仅 `localhost`/`127.0.0.1`/`.local` 允许 `ws://`；
> 删除硬编码 `101.37.80.51`（L153）与 `exceptionDomain`（tauri.conf L44）

`04_数据安全与可靠性.md` E-01：
> 客户端 `toWsUrl()` 默认产出 `wss://`；明文 `ws://` **仅在** `serverUrl` 为
> `localhost`/`127.0.0.1`/`.local` 时允许（本地开发豁免），其余一律拒绝并提示

`06_测试验收与风险清单.md` S1 验收：
> `toWsUrl`（`storage.ts`，S1）：公网域名→`wss://`、`localhost`/`127.0.0.1`/`.local`→允许 `ws://`、非法输入→空串

⇒ **协议由主机名推导**（公网默认 wss、明文本机豁免、其余拒绝并提示），
比「给用户一个开关」更严也更简单：**不存在能让用户点出降级的路径**。

## 3. 改动清单

### 3.1 client `src/services/storage.ts` —— 协议裁决的唯一入口

- 新增 `parseScheme` / `cleanAddress` / `isLocalHost` / `describeWsUrl`。
- `toWsUrl` 改为 `describeWsUrl(address).url`（**不再自己拼协议**）。
- `describeWsUrl` 的规则（与台账逐条对应）：
  | 输入 | 结果 |
  |---|---|
  | 显式 `wss://` | `wss://host` —— **原样保留，绝不降级** |
  | 显式 `ws://` + 本机 | `ws://host` |
  | 显式 `ws://` + 公网 | **拒绝**（`url=""` + 说明「请配 TLS_KEY_PATH/TLS_CERT_PATH」） |
  | 无协议 + 本机 | `ws://host`（本地开发豁免） |
  | 无协议 + 公网 | `wss://host`（**安全默认**） |
  | 非法输入 | **拒绝**（`url=""` + 格式说明） |
- `hydrateStorage` **不再剥协议**（原来 `displayUrl` 会把显式 `wss://` 抹掉，
  本机地址重启后回落成明文 `ws://`）；预设条目的迁移同步改为保留协议。
- `DEFAULT_SETTINGS.serverUrl` 由写死的公网 IP 改为 **空串**。
- 删掉 `stripToken`（`new URL` 对裸地址是「碰巧能跑」），统一用 `cleanAddress`。

### 3.2 client UI —— 如实显示实际连接方案，而不是给一个会骗人的开关

- `LoginView.tsx`：
  - 删掉本轮早先加的「传输方式」单选（TLS / 明文）——**它是个陷阱**：
    界面能勾「明文」，但公网地址下 `toWsUrl` 会直接拒绝，用户点了连不上却不知道为什么。
  - 改为 `Alert` **如实显示**「按这个地址实际会怎么连」：
    `将使用 TLS：wss://…` / `将使用明文：ws://…（仅限本机）` / 连不上时显示拒绝原因。
  - `doAuth` 改用 `describeWsUrl` 裁决；地址非法或被拒时**在提交前**就提示。
  - 自动连接：地址连不了时**跳过**并提示，不再去连一个空地址（那只会得到一句看不懂的「连接失败」）。
  - 存的是**实际会用到的地址**（含协议）⇒ 本机 + 显式 `wss://` 不会被回落成明文。
- `SettingsPanel.tsx`：
  - `onSave` 原来用 `displayUrl(draft.serverUrl)` —— **那会把协议一起剥掉**，
    「用户显式填的 `wss://`」在保存那一刻就被降级了。改为 `cleanAddress` + `describeWsUrl`。
  - 预设列表显示裸主机名（`displayUrl`），但**存储**的是解析后的完整地址。
- `App.tsx` / `MainView.tsx`：`toWsUrl(...)` → `describeWsUrl(...).url`，
  并在地址连不了时**不发起**自动连接 / 不打相对路径请求。
- `api.ts` `serverUrlToHttpBase`：**空串原样返回空串**（原来 `new URL("")` 抛异常后
  回退成原值，会让 fetch 打到一个相对路径上，报出与真实原因无关的错）。

### 3.3 client —— 假加密字段**双侧删除**（S1-B09/B10）

- `src/types.ts`：`REGISTER_SUCCESS` 的 `encryptionKey?: string` 删除。
- `src/stores/sessionStore.ts`：`encryptionKey` 字段与 `setEncryptionKey` 删除。
- `src/App.tsx`：`setEncryptionKey(msg.encryptionKey ?? null)` 删除。
- server `server.js`：`REGISTER_SUCCESS` 不再下发 `encryptionKey`。

> 为什么不改成「随机值」：留着一个叫 `encryptionKey` 的字段，就会让用户以为链路是加密的，
> 而它其实什么都不是。**给用户「已加密」的错觉，比不加密更危险**（台账 04 的原话）。
> 老客户端读到这个字段会得到 `undefined` —— 它本来就从未参与过任何加解密，无功能影响。

### B. 台账功能欠账 S1-B16 / Z-08：一键互控真正闭环

服务端 `CONTROL_ACCEPT` 原先只读 `msg.targetId`，而真实客户端
`signaling.acceptControl()` 发的是 `fromId` ⇒ 服务端拿到 `undefined`：
不建会话、不回执、不授权，「接受控制」点了等于没点。同时 `CONTROL_ACCEPTED`
从不携带 `{sessionId,sessionToken,role}`，控制端即使进了 controlling 也收不到帧。

现已落地（`server.js`）：

1. `CONTROL_ACCEPT` 同时接受 `fromId` / `targetId`；请求方离线时回 `CONTROL_FAILED`。
2. 显式会话：沿用原会话，补成员、授权、回 `CONTROL_ACCEPTED{sessionId}` 与 `CLIENT_JOINED`。
3. 一键互控（无显式会话）：**服务端建会话**，向被控端发 `SESSION_CREATED`，
   向请求方回 `CONTROL_ACCEPTED{sessionId,sessionToken,role:"client"}`。
4. `CONTROL_REQUEST` 的 `sameUser` 改由服务端按设备归属计算（原先客户端读的是死字段 S-16），
   并透传 `ephemeral` / `requestedPermission` / `sasHash`。
